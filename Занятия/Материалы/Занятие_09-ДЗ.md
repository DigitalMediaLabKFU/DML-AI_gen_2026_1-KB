
## Важно про окружение

Для выполнения **обязательной части** домашнего задания достаточно:
- материалов занятия;
- демонстрации преподавателя;
- ваших заметок;
- текущего `GDD.md`;
- `style-bible.md`;
- уже имеющихся selected outputs.

**Для выполнения дополнительных задач недостаточно только cloud.comfy.org.**

Дополнительные практические задачи с IP-Adapter / Flux 2 Klein / локальным upscale требуют:
- доступа к серверу, предоставляемому преподавателем;
- или собственного локального ComfyUI;
- или другого самостоятельно настроенного способа запуска пайплайнов занятия.

Эти дополнительные задачи выполняются **по возможности и желанию**. Они не являются обязательными для базовой сдачи.

## Этап 0 — если на занятии НЕ успели: довести базовые notes до минимального состояния

**Когда делать:** если на занятии вы не успели заполнить `workflow-notes.md`, reference rules или список кандидатов на upscale.

### Что сделать

1. Открыть:
   - `logs/workflow-notes.md`
   - `style/style-bible.md` или `GDD.md`
   - папку `outputs/selected/` или `images/selected/`

2. Создать в `logs/workflow-notes.md` раздел:

```md
## W09 — IP-Adapter / Flux 2 / Flux 2 Klein / Simple Upscale
```

3. Кратко заполнить:

   * что показал преподаватель по IP-Adapter;
   * что показал преподаватель по Flux 2 Klein;
   * какие ограничения есть у cloud.comfy.org;
   * какие подходы могут быть полезны вашему проекту;
   * какие 2 ассета вы потенциально хотите довести через upscale.

4. Если нет готовых изображений, описать **2 будущих ассета-кандидата** текстом.

**Готово, если:**

* в `workflow-notes.md` есть базовая заметка по занятию;
* есть хотя бы черновое понимание, где применим IP-Adapter, где Flux 2, а где upscale;
* выбраны или описаны 2 кандидата на upscale.

## Задача 1 — `logs/workflow-notes.md`: сравнительная заметка по подходам

**Цель:** показать, что вы понимаете различия между IP-Adapter, Flux 2-подходами, Flux 2 Klein и простым upscale.

### Добавить в `logs/workflow-notes.md` раздел:

```md
## W09 — IP-Adapter / Flux 2 / Flux 2 Klein / Simple Upscale
```

### Обязательно заполнить таблицу:

```md
| Подход | Что делает | Где полезен в моём проекте | Ограничения | Нужен ли мне сейчас |
|---|---|---|---|---|
| IP-Adapter | | | | |
| Flux 2 / image editing | | | | |
| Flux 2 Klein | | | | |
| Simple upscale | | | | |
```

### Что важно указать

#### IP-Adapter

* для каких задач он может пригодиться;
* какие референсы можно подключать;
* что он переносит лучше всего:

  * стиль;
  * композицию;
  * цвет;
  * общий визуальный вайб;
* где есть риск копирования;
* почему это не универсальный способ для всего.

#### Flux 2 / image editing

* для каких задач он интересен;
* где полезна работа с изображением как входом;
* где может пригодиться multi-reference;
* почему этот подход может быть недоступен в cloud;
* нужен ли он вашему проекту сейчас или позже.

#### Flux 2 Klein

* что было показано на демонстрации;
* где запускался пайплайн;
* какие компоненты важны:

  * `diffusion_model`;
  * `text_encoder`;
  * `VAE`;
* почему запуск не является обязательным для всех;
* где Klein может быть полезен для быстрых локальных итераций.

#### Simple upscale

* какие изображения стоит апскейлить;
* какие изображения не стоит апскейлить;
* что upscale улучшает;
* что upscale не исправляет.

**Готово, если:**

* таблица заполнена не общими словами, а применительно к вашему проекту;
* есть вывод: какие подходы вы реально будете использовать дальше;
* ограничения окружения зафиксированы честно.

## Задача 2 — `style/style-bible.md` или `GDD.md`: обновить правила работы с референсами

**Цель:** превратить работу с референсами из “сделай похоже” в понятную производственную систему.

### Добавить или обновить раздел:

```md

```

### Минимальная структура

```md
## Reference rules

- Палитра:
- Свет:
- Композиция:
- Материалы:
- Настроение:
- Поза / силуэт:
- Камера / ракурс:

### Что не копируем

- Узнаваемых персонажей:
- Логотипы и бренды:
- Лицо реального человека:
- Уникальный дизайн чужого IP:
- Точную форму костюма / символику:
- Композицию один в один, если она слишком узнаваема:

### Как проверяем результат

- Ассет поддерживает GDD:
- Ассет совпадает со style bible:
- Из рефа перенесены только отдельные качества:
- Результат не выглядит копией:
- Изображение можно использовать для Midterm / Final:
```

### Дополнительно

Добавить 2–3 конкретных примера ваших референсов:

```md
| Реф | Что берём | Что не копируем | Для какого ассета |
|---|---|---|---|
| ref-01 | | | |
| ref-02 | | | |
| ref-03 | | | |
```

**Готово, если:**

* преподаватель понимает, как вы будете использовать референсы дальше;
* правила помогают писать prompt’ы и отбирать изображения;
* есть не только “что нравится”, но и “что запрещено”.

## Задача 3 — подготовить 2 кандидата на будущий upscale

**Цель:** выбрать не случайные красивые картинки, а изображения, которые действительно стоит доводить к Midterm / Final.

### Вариант A — если у вас уже есть selected outputs

Выберите 2 изображения из:

* `outputs/selected/`
  или
* `images/selected/`

Добавьте в `logs/workflow-notes.md` таблицу:

```md
## Upscale candidates

| Файл | Роль в проекте | Почему кандидат | Что исправить до upscale | Решение |
|---|---|---|---|---|
|  |  |  |  |  |
|  |  |  |  |  |
```

### Для каждого кандидата указать

1. **Роль в проекте**

   * персонаж;
   * локация;
   * проп;
   * скринген;
   * mood-shot;
   * UI / интерфейсный кадр.

2. **Почему его стоит апскейлить**

   * хорошо показывает мир;
   * связан с core loop;
   * подходит для Midterm;
   * поддерживает style bible;
   * может стать основой финального скрингена.

3. **Что нужно исправить до upscale**

   * руки;
   * лицо;
   * мелкие артефакты;
   * шум;
   * слабый фон;
   * недостаточная читаемость.

4. **Решение**

   * `ready`;
   * `fix first`;
   * `drop`;
   * `regenerate`.

### Вариант B — если подходящих изображений нет

Описать 2 будущих ассета:

```md
| Будущий ассет | Роль в проекте | Какие рефы нужны | Какой подход попробовать | Почему это кандидат на upscale |
|---|---|---|---|---|
|  |  |  |  |  |
|  |  |  |  |  |
```

**Готово, если:**

* выбраны или описаны 2 кандидата;
* понятно, зачем они проекту;
* понятно, что нужно сделать перед upscale;
* upscale не используется как попытка спасти плохой кадр.

## Задача 4 — `GDD.md`: обновить визуальный пайплайн проекта

**Цель:** связать выводы занятия с основным документом проекта, а не оставить их отдельной технической заметкой.

### Добавить или обновить в `GDD.md` короткий раздел:

```md
## Visual production pipeline
```

### Что указать

1. Какие типы ассетов вы будете делать через обычный ComfyUI workflow:

   * txt2img;
   * img2img;
   * inpaint;
   * ControlNet;
   * другое.

2. Где могут пригодиться референсы:

   * стиль;
   * композиция;
   * поза;
   * материал;
   * окружение;
   * UI-мотив.

3. Какой подход к рефам вы планируете использовать:

   * IP-Adapter;
   * Flux 2 / image editing;
   * Flux 2 Klein;
   * обычный prompt + style bible;
   * пока только подготовка рефов и prompt skeleton.

4. Какие ассеты пойдут в upscale:

   * кандидат 1;
   * кандидат 2;
   * почему именно они.

### Объём

* 1 короткий раздел;
* ориентир: **5–10 строк** осмысленного текста или таблица.

**Готово, если:**

* преподаватель открывает `GDD.md` и понимает, как вы собираетесь дальше производить визуальные ассеты;
* выводы занятия связаны с проектом;
* есть связь с future selected outputs, Midterm и Final.

## Задача 5 — `logs/workflow-notes.md`: зафиксировать ограничения окружения

**Цель:** честно описать, что доступно в вашем рабочем контуре, а что было только демонстрацией.

### Добавить блок:

```md
## Environment limitations

- Основной контур работы:
- Что доступно в cloud.comfy.org:

- Что я могу запустить локально:
```

### Что можно указать

* ComfyUI Cloud доступен, но нужный IP-Adapter workflow отсутствует.
* Flux 2 Klein был показан на сервере преподавателя.
* Локальный ComfyUI не настроен.
* Собственный GPU отсутствует.
* Есть возможность запросить доступ к серверу преподавателя.
* Дополнительные генерации выполнять не планирую, делаю аналитическую часть.
* Планирую попробовать локальный запуск позже.

**Готово, если:**

* понятно, какие результаты реально воспроизводимы у вас;
* понятно, какие результаты относятся к demo преподавателя;
* нет ложного впечатления, что вы запускали то, чего не запускали.

Это нормально. Базовая домашка всё равно выполняется.

* reference rules;

**Важно:** отсутствие доступа к вычислениям не освобождает от проектных выводов.

## Важно

* **Главное в этой домашке — не количество генераций, а выбор подхода под задачу проекта.**
* **IP-Adapter — полезный инструмент, но не универсальное решение.**
* **Flux 2 Klein — демонстрационный и опциональный путь, если есть доступ к серверу или локальному запуску.**
* **Upscale стоит делать только для удачных кадров.**
* **Референс — это источник отдельных качеств, а не объект для копирования.**
* **Selected — это кураторский набор, а не склад всех файлов.**
* **Все выводы должны быть связаны с GDD, style bible и будущими скрингенами.**
